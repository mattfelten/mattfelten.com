Component

Checklist

A list of items you can tick, reorder, edit in place, and nest one level deep. Built for Collaboration Loops, and adopted by Runbooks.

In review

Example

Running, not a screenshot. Pick a state and the specimen and the address change together.

Open

Every state above is a named value in the address. Values the component does not recognise are ignored rather than guessed at, so a wrong one renders the default instead of something invented. The dimmed parameters are frame plumbing: they size the specimen inside a page and say nothing about the component.

Anatomy

Three levels. The list owns order and nothing else. A row is the arbiter between its parts, and a sub-item is a real row with exactly the same parts, which is why nesting is a capability rather than a second component.

Props

Every capability is off by default, and turning one on brings its whole surface with it. The things that are not props are the things a consumer should not be able to get wrong.

PropTypeDefaultWhat it does
items ChecklistItem[] required Order comes from the array. The component never sorts. Each item carries its own presence.
reorderable boolean false The handle and the Move up / Move down menu items, together. Never one without the other.
nesting boolean false One level, or none. False withdraws the gesture and the affordance, and flattens the data.
editable boolean false Inline edit and autosave. Who may edit is the consumer's call, not this flag.
showCreator boolean false The author tag. Runbooks does not want one.
composerLabel string? "Add an item" Placeholder on the add row. Runbooks says "Add a step".
onReorder, onEdit,
onCreate, onDelete		 callbacks - Intent out, new items in. The component holds no server state.

There is no prop for target size, for how a completed row fades, for whether a parent cascades to its children, or for locking a row while somebody is in it. Each of those was decided once, and exposing it would let a consumer decide it again and worse.

Data

A row is five fields and a boolean. parentId is the entire nesting model: one nullable field is what one level costs in the data, which is why turning nesting off can flatten rather than migrate. 

type ChecklistItem = {
  id: string
  text: string                // markdown
  checked: boolean            // the box, not your meaning
  author: string              // the creator badge
  parentId: string | null     // the whole nesting model
  presence?: PresenceUser[]   // who is in THIS row
}

type PresenceUser = {
  id: string
  name: string          // announced, not just drawn
}

Callbacks

const move = (id, { after, before }) => api.reorder(...)   // neighbours, never an index
const save = (id, text) => api.updateItem(id, text)            // fires on autosave, not on blur

Reorder takes neighbour ids rather than an index, so the server resolves the position inside the transaction and two people reordering at once cannot write the same slot. checked, not done: the component knows the box is ticked, not what that means to you.

States

What a row can be, and what it looks like when it is. Where a state has an address of its own the name links to it, and the example above changes to match. The four that do not are things the specimen does under your cursor rather than states you can open.

StateWhenTreatment
default Resting. No handle, no menu. Both arrive on hover so a resting list is a list.
hover Pointer over the row. Row tint. The handle and the kebab appear in the gutters, which are reserved whether or not anything is in them.
checked Box ticked. Text fades to 60%, which measures 4.58:1. The author's name is not faded at all.
editing Text clicked, or Edit from the menu. No border, no padding, no growth. The field has no edges, so nothing below it moves.
focused Keyboard focus anywhere in the row. Hover tint plus a ring on the row's own edge, keyed off focus-within. Painted, never laid out.
occupied Somebody else is in the row. An avatar in the left gutter, and nothing else. No dim, no bar. Announced by name, not only drawn.
dragging Row lifted. A collapsed proxy follows the cursor and an insertion line shows where it lands. Only the gaps it can land in are offered.
nested parentId is set. Indented one step. Identical parts. A sub-item cannot itself be a parent.
coarse pointer pointer: coarse. The edit affordance becomes permanent instead of hover-only, and the menu opens on long press.
forced colors forced-colors: active. Background and box-shadow are dropped by the mode, so every painted state is repaired with outline.

Accessibility

Audited against eight areas. The headline is a correction rather than a confirmation: a keyboard path was necessary and was never sufficient. SC 2.5.7 asks for a single pointer alternative to any drag, and a keyboard is not one.

Colour contrast
Completed items dim to 60%, which measures 4.58:1. They shipped at 50%, which is 3.35:1 and fails.
Target size
Checkbox, handle and kebab are 24 by 24, the 2.5.8 minimum, grown with a negative margin so the glyph does not move.
Keyboard
Every row action has a keyboard path. Move up and Move down live in the row menu, so reordering never needs a drag.
Pointer gestures
The menu is the single pointer alternative, and it covers touch and screen readers for free.
Touch
Tapping the text already edited it and nothing said so. The affordance becomes permanent under pointer: coarse.
Screen reader
A nested list, not a tree. One level does not earn the arrow-key contract a tree takes over.
Focus visible
The field has no edges, so focus cannot be the field appearing. Painted with background and shadow, which sit outside layout.
Reduced motion
The drop animation and the presence entrance both respect it. Nothing conveys state by movement alone.

What the consumer owes

Use object names
Pass a label. The component renders a group of checkboxes and does not know what they are a list of.
Include a section heading
The component owns one region, not the page. Give it a heading somebody can navigate to.
Handle permissions
Set editable per row from your own rules. The component asks the question and never answers it.
Name the people
Presence is announced, not just drawn. Without a name it is an anonymous face a screen reader cannot report.

Usage

Two consumers, four lines of configuration apart. Runbooks is the shorter call, and it never has to know that reordering, presence and the author tag exist.

Rules

Do

  • Pass a label and a heading. The component owns one region, not the page, and it does not know what its items are a list of.
  • Decide who may edit, per row. The editable prop turns the capability on. Your rules decide who gets it.
  • Give every presence user a name. An avatar without one is a face a screen reader cannot report.
  • Resolve order on the server from the neighbour ids onReorder hands you, inside the transaction.
  • Handle a failed save yourself. There is no Save button, so there is no place for a failed write to land, and a silent failure is silent data loss.

Do not

  • Do not sort items. Order comes from the array, and the component never touches it.
  • Do not cascade a tick to children. Multiplayer decides this: cascading silently writes to rows other people wrote.
  • Do not lock a row while somebody is in it. Merging at save removed the reason for one, and a lock trains a habit that has to be untrained.
  • Do not read checked as done. A checked runbook step is complete. A checked discussion item might be agreed, covered, or dropped.
  • Do not nest past one level. A sub-item cannot be a parent, and the ceiling is enforced by not offering, never by refusing.
